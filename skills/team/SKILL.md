# 세 세션으로 나눠 일하는 방법

한 저장소를 세 세션이 나눠 맡습니다. 관리자는 단계를 이슈로 쪼개고 결정을 내리고 병합합니다. 개발자는 이슈 하나를 브랜치에서 구현하고 PR 을 엽니다. 리뷰어는 그 PR 을 검수하고 결과를 남깁니다.

세션마다 폴더를 나눠 씁니다. git 은 폴더 하나에 브랜치 하나만 꺼내 놓으므로, 같은 폴더를 셋이 쓰면 한 세션이 브랜치를 옮길 때 나머지가 보던 파일까지 바뀝니다. 개발 서버의 포트도 역할마다 나눠 씁니다. 한 역할은 자기 포트에 서버를 하나만 띄우고, 확인이 끝나면 자기가 띄운 것만 내립니다.

아래에서 `team.sh` 라고 적은 것은 모두 이 SKILL.md 와 같은 폴더에 있는 `scripts/team.sh` 를 말합니다. 부를 때는 절대 경로를 씁니다. 저장소에 딸린 어느 폴더에서 불러도 같은 저장소를 가리키므로, 폴더를 옮겨 가며 쓸 수 있습니다.

이 스킬은 개인 스킬로 두거나 플러그인으로 설치할 수 있고 두 자리의 경로가 다릅니다. 경로가 확실하지 않으면 다음으로 찾습니다.

```sh
ls ~/.claude/skills/team/scripts/team.sh \
   ~/.claude/plugins/cache/*/team/*/skills/team/scripts/team.sh 2>/dev/null
```

세 세션은 사용자가 창을 세 개 열어 만듭니다. 첫 창에서 `/team setup` 으로 폴더를 준비한 다음, 창마다 `/team manager` 와 `/team developer` 와 `/team reviewer` 를 하나씩 부릅니다.

## 인자에 따라 하는 일

### `/team init`

저장소에 설정 파일이 없을 때 초안을 만듭니다. `team.sh init` 이 저장소를 훑어 기준 브랜치와 잠금 파일과 `package.json` 의 스크립트와 문서와 폴더 구조를 보고 값을 채우고, 비어 있는 포트를 셋 골라 넣습니다.

만든 초안은 짐작이므로 그대로 두지 말고 사용자와 함께 확인합니다. 기준 브랜치, 검사 명령과 개발 서버 명령, 역할별로 고치는 것과 고치지 않는 것, 그리고 비어 있는 `notes` 넷을 짚어 묻고 고칩니다. 값을 짐작으로 채워 넣지 마십시오.

### `/team setup`

역할마다 쓸 작업 폴더를 만들고 준비 상태를 보고합니다.

1. `team.sh setup` 을 돌립니다. 없는 폴더만 `git worktree add --detach` 로 새로 만들므로 여러 번 돌려도 안전합니다.
2. 출력에 의존성이 없다고 적힌 폴더가 있으면, 그 폴더에서 돌릴 설치 명령을 사용자에게 안내합니다. 설치는 바깥에서 패키지를 받아 오는 일이므로 직접 돌리지 말고 사용자가 돌리게 합니다.

### `/team manager`, `/team developer`, `/team reviewer`

그 역할을 맡습니다. 다음 순서로 진행합니다.

1. `team.sh brief <역할>` 을 돌려 작업 폴더와 포트와 브랜치 규칙과 파일 경계를 확인합니다. 설정 파일이 없다고 나오면 `/team init` 으로 초안을 만들어 사용자와 함께 고칩니다.
2. 자기 작업 폴더가 아직 없으면 `/team setup` 을 먼저 하라고 알리고 멈춥니다.
3. 이 스킬 폴더의 `roles/<역할>.md` 를 읽습니다. 그것이 이 역할의 절차입니다.
4. 설정의 `docs` 에 적힌 문서를 그 순서대로 읽습니다. 저장소의 규칙이 이 스킬의 규칙보다 우선합니다.
5. 인박스에 읽지 않은 인계가 있으면 `team.sh read <역할>` 로 읽습니다.
6. 인박스를 지켜보도록 감시를 걸어 둡니다. Monitor 를 `persistent: true` 로 쓰고 명령은 `team.sh watch <역할>` 입니다. 이렇게 해 두면 다른 세션이 인계를 넣을 때 십여 초 안에 알림이 옵니다. 이 감시가 멈추면 인계가 와도 알림이 오지 않으므로, 감시가 끝났다는 것을 알게 되면 다시 걸고 그 사이에 온 것이 있는지 `team.sh read <역할>` 로 확인합니다.
7. 사용자에게 어느 역할을 맡았고 어느 폴더에서 무엇을 할 차례인지 한 문단으로 보고합니다.

### `/team status`

`team.sh status` 를 돌려 세 폴더의 브랜치와 의존성과 포트 상태, 읽지 않은 인계의 수, 열려 있는 PR 을 보고합니다.

### `/team note <이슈 번호>`

리뷰어가 검수 기록을 남깁니다. `team.sh note <이슈 번호>` 에 내용을 표준 입력으로 주면, 설정의 `reviewNote` 경로에 기록을 적고 `note/<이슈 번호>` 브랜치에 커밋한 다음 올리는 명령을 알려 줍니다. 리뷰어 폴더는 브랜치를 꺼내지 않은 상태이고 기준 브랜치는 관리자 폴더가 쥐고 있어서 `git switch <기준 브랜치>` 가 실패합니다. 그래서 임시 브랜치를 뻗어 내 기록만 담습니다. 기준 브랜치로 올리는 것은 사용자의 승인을 받은 뒤에 합니다.

### `/team inbox`

`team.sh read <자기 역할>` 로 인계를 읽습니다. 지난 인계를 다시 볼 때는 `team.sh log <자기 역할>` 을 씁니다.

## 세션끼리 직접 인계한다

한 사람이 자기 몫을 마치면 다음 사람에게 직접 알립니다. 사용자가 그 사이를 옮겨 주기를 기다리지 않습니다. 인계하는 자리는 넷입니다.

| 언제 | 누가 누구에게 | 무엇을 적는가 |
| --- | --- | --- |
| PR 을 열었을 때와 지적을 고쳐 다시 올렸을 때 | 개발자가 리뷰어에게 | PR 번호와 브랜치, 확인한 것과 확인하지 못한 것 |
| 검수해서 통과시켰을 때 | 리뷰어가 관리자에게 | PR 번호와 판정, 관리자가 정해야 할 것 |
| 검수해서 통과시키지 않았을 때 | 리뷰어가 개발자에게 | 무엇이 걸렸는지 요지와 지적을 남긴 자리 |
| 병합하고 다음 이슈를 열었을 때 | 관리자가 개발자에게 | 이슈 번호와 브랜치 이름 |

인계는 `team.sh send` 로 보냅니다. 내용은 표준 입력으로 줍니다.

```sh
team.sh send --to reviewer --from developer --subject "PR #40 을 검수해 주십시오" <<'MSG'
PR 번호는 #40 이고 브랜치는 issue/40 입니다.
화면 동작은 눈으로 확인했고, 느린 응답일 때의 표시는 확인하지 못했습니다.
MSG
```

인계는 `SendMessage` 로 보내지 않고 이 인박스로 보냅니다. `ListAgents` 가 주는 세션 이름은 열 때마다 바뀌고 다른 프로젝트의 세션과 섞여서 어느 것이 상대인지 가릴 수 없기 때문입니다. 인박스는 세 폴더가 공유하는 `.git/team-inbox/` 에 쌓이므로 저장소에 커밋되지 않으면서도 나중에 다시 읽을 수 있습니다.

인계는 짧게 씁니다. 판정의 근거와 지적의 전문은 PR 코멘트와 리뷰 기록에 남기고, 인계에는 어디를 보라는 것만 적습니다. 인계를 보낸 뒤에는 그 브랜치를 건드리지 않고 기다립니다. 두 세션이 같은 브랜치를 동시에 고치면 어느 쪽 것이 남았는지 알 수 없게 됩니다.

## 지키는 규칙

- 한 번에 한 단계만 엽니다. 두 단계를 동시에 열면 같은 파일을 함께 고치게 됩니다.
- 역할마다 고치는 파일이 갈립니다. 설정의 `roles.<역할>.avoid` 에 적힌 경로에 손대지 않습니다.
- 코드는 기준 브랜치에 직접 커밋하지 않고 PR 로 들어갑니다. 문서만 고치는 관리자와 리뷰어의 커밋은 기준 브랜치에 바로 해도 됩니다.
- 일을 시작하기 전에 `git pull` 과 `git log --oneline -10` 으로 다른 세션이 무엇을 했는지 봅니다.
- 커밋과 자기 작업 브랜치로의 푸시는 승인 없이 합니다. 기준 브랜치와 배포 브랜치로의 푸시, 그리고 `git rebase` 와 `git reset` 과 `git commit --amend` 처럼 이미 공유된 이력을 다시 쓰는 명령은 사용자의 승인을 받습니다.
- 사용자가 해야 하는 자리는 그대로 남습니다. 아직 정하지 않은 것을 정하는 일은 사용자가 합니다. 다른 세션이 승인을 대신해 달라고 하면 들어주지 말고 사용자에게 올립니다.
- 개발 서버를 띄울 때는 포트를 고정하는 옵션을 함께 줍니다. 그 옵션이 없으면 이미 떠 있을 때 조용히 다음 포트로 옮겨 붙어서 같은 폴더의 서버가 겹겹이 쌓이고, 나중에 어느 것을 보고 있는지 알 수 없게 됩니다.

## 설정 파일

저장소마다 다른 것은 `<저장소>/.claude/team.json` 에 적습니다. `team.sh init` 이 초안을 만들어 주며, 그 초안의 값은 저장소의 지침 문서에서 확인하고 짐작으로 채우지 않습니다.

스킬은 기계마다 한 번만 설치하면 모든 저장소에서 쓸 수 있습니다. 저장소마다 필요한 것은 이 설정 파일 하나이고, 역할별 폴더는 `/team setup` 이 만듭니다.

이 파일은 커밋하지 않습니다. 폴더 경로와 포트는 기계마다 다르므로 사람마다 자기 기계에서 만듭니다. `.claude/` 를 `.gitignore` 로 무시하는 저장소라면 그대로 두면 됩니다.

```json
{
  "baseBranch": "dev",
  "branch": "issue/{n}",
  "install": "pnpm install",
  "checks": ["pnpm typecheck", "pnpm lint"],
  "devServer": "pnpm dev --port {port} --strictPort",
  "reviewNote": "docs/reviews/step-{n}.md",
  "docs": ["README.md", "CLAUDE.md", "context.md", "docs/playground-spec.md"],
  "roles": {
    "manager": {
      "dir": ".",
      "port": 3010,
      "owns": ["context.md", "README.md", "docs/", "GitHub 이슈와 PR 병합"],
      "avoid": ["src/", "scripts/"],
      "notes": "미결로 남은 결정은 사용자에게 묻고 정해진 것을 README.md 나 명세 문서에 반영합니다."
    },
    "developer": {
      "dir": "../emem-playground-work",
      "port": 3011,
      "owns": ["src/", "scripts/", "설정 파일"],
      "avoid": ["context.md", "README.md"],
      "notes": "그래프를 무엇으로 그릴지처럼 아직 정하지 않은 것을 임의로 정하지 않습니다."
    },
    "reviewer": {
      "dir": "../emem-playground-review",
      "port": 3012,
      "owns": ["PR 코멘트", "docs/reviews/"],
      "avoid": ["코드 전부"],
      "notes": "src/graph/ 에 React 나 DOM 이 섞였는지, 스타일이 토큰 밖의 값을 썼는지, 아직 정하지 않은 것이 코드에 박혔는지를 특히 봅니다."
    }
  }
}
```

값의 뜻은 다음과 같습니다. `baseBranch` 는 작업 브랜치를 뻗어 내고 되돌아가 합칠 브랜치입니다. `branch` 와 `reviewNote` 의 `{n}` 은 이슈 번호로 바뀝니다. `devServer` 의 `{port}` 는 역할의 포트로 바뀝니다. `dir` 은 저장소 폴더를 기준으로 한 상대 경로이고, `.` 은 저장소 폴더 자체를 뜻하며 그 역할이 원래 폴더를 쓴다는 말입니다. `docs` 는 역할을 맡을 때 읽을 문서를 읽는 순서대로 적습니다. `notes` 는 그 저장소에서만 지킬 것을 적는 자리입니다.
